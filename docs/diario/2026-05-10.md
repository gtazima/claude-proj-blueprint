# 2026-05-10 — Implementação do Supabase Auth

## O que foi feito

### Decisão: troca de Cloudflare Access por Supabase Auth

O plano original era usar Cloudflare Access (email OTP) como camada de autenticação, mas descobrimos uma limitação da plataforma: **Cloudflare Access não funciona em domínios `*.workers.dev`**. Como o frontend está em `agroecologia.g-tazima.workers.dev`, Cloudflare Access é inviável sem um domínio próprio.

Decisão: usar **Supabase Auth diretamente** (JWT HS256), aproveitando o banco Supabase que já estava no projeto.

---

### Backend (`src/api/`)

- `PyJWT 2.12.1` adicionado ao `pyproject.toml`
- `config.py` — novo campo `supabase_jwt_secret: str = ""`
- `deps.py` — dependência `get_current_user()` com verificação HS256 + audience `"authenticated"`
- `main.py` — router de tasks protegido com `dependencies=[Depends(get_current_user)]`
- `.env.example` — documentado `SUPABASE_JWT_SECRET`

---

### Frontend (`src/web/`)

- `@supabase/supabase-js 2.105.4` instalado
- `src/lib/supabase.ts` — cliente Supabase (usa `VITE_SUPABASE_URL` + `VITE_SUPABASE_ANON_KEY`)
- `src/contexts/AuthContext.tsx` — provider com `signInWithEmail`, `signInWithGoogle`, `signOut`
- `src/pages/Login.tsx` — página de login (email/senha + botão Google OAuth)
- `src/App.tsx` — `AuthProvider` wrapping o app + guard `ProtectedRoutes` + rota `/login`
- `src/components/Layout.tsx` — email do usuário logado + botão "Sair" no rodapé da sidebar
- `src/api/tasks.ts` — cabeçalho `Authorization: Bearer <token>` em todas as chamadas à API
- `.env.example` — documentado `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `VITE_API_URL`

## Decisões tomadas

| Decisão | Justificativa |
|---|---|
| Supabase Auth no lugar de Cloudflare Access | Cloudflare Access não funciona em `*.workers.dev` — limitação da plataforma |
| JWT HS256 + audience `"authenticated"` | Padrão do Supabase Auth — sem overhead de biblioteca extra |
| Google OAuth na tela de login | Supabase suporta nativamente; usuário principal tem Google — menos fricção |
